# Project adoption

Establish the product's actual owners, URLs, providers, existing data and required visitor journeys before replacing template defaults. Preserve existing settings and record the starter revision for future updates.

Confirm authentication, resource ownership and the database plan before enabling protected mutations or changing migration history. A fail-closed starter is not an implemented account system. Public flows need their own validation, duplicate behavior and abuse policy.

Replace demo facts and assets only with approved material. Agree on canonical URLs, redirects, indexing, analytics/consent and content ownership. Do not infer product approval from a working example. If a CMS is required, verify a real editing and publishing task.

Use isolated credentials, origins and disposable databases for development. Provider accounts decide real-world payment and delivery behavior; a deployment label alone is not a safe staging boundary. Ask before migrations, live actions or deployment.

Reuse the existing source conventions and command configuration. Remove inherited examples as a complete slice only when the product's replacement and recovery plan are clear. Report remaining owner decisions rather than filling them with plausible values.
